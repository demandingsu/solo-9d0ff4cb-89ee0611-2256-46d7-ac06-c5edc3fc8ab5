# 骑行赛计时复核

同一名车手的主/备计时读数导入后，逐圈核定读数，并判断“最快一圈”能否确定打破现有纪录。全程用 Flask + SQLite，可直接用 Docker Compose 启动。

## 启动

```bash
docker compose up --build
```

打开 <http://localhost:8000>。数据保存在 Compose 命名卷 `race-data` 中；生产环境请设置 `SECRET_KEY`：

```bash
SECRET_KEY="$(openssl rand -hex 32)" APP_PORT=8000 docker compose up --build
```

CSV 列（英文或中文表头均可）：

```csv
lap,source,cumulative_ms
1,主计时,74210
1,备计时,74230
2,主计时,148900
2,备计时,148870
```

支持别名：`lap`/`圈号`、`source`/`计时来源`、`cumulative_ms`/`发车后累计毫秒数`；来源 `主计时`/`备计时`（也接受 `主`/`备`/`primary`/`backup`）。圈号必须从 1 起连续；同一圈同一来源只能有一条读数。

## 计时来源核查

批次详情页可上传两份来源核查 CSV。它们与读数分开导入，可分别补交。

关联表——把每个圈的主/备读数接到计时事件：

```csv
lap,source,event_id
1,主计时,P-1001
1,备计时,B-2001
```

事件登记表——为每个事件登记**上游事件号**或**原始设备号**（二选一，必填其一）：

```csv
event_id,upstream_event_id,raw_device_id
P-1001,UP-77,
B-2001,UP-77,
UP-77,,DEV-A
```

支持别名：`event_id`/`事件号`/`事件编号`、`upstream_event_id`/`上游事件号`、`raw_device_id`/`原始设备号`。关联表也可只交一部分圈。

沿 `upstream_event_id` 一路向上，直到某个事件带 `raw_device_id`；该事件为**原始事件**，该设备为物理计时来源。逐圈判定：

- 主备读数都追到同一原始事件/设备 → **同一台设备**（可能共用了同一个数据来源）。
- 追到两个不同设备 → **两台设备**。
- 任一侧缺读数、未关联事件、链中断或链成环 → **证据不全**。

同一个原始事件被不同圈引用时，页面按原始事件汇总，列出所有涉及的圈、来源、累计时间和各自的来源链。

补交规则：

- 每次可只交一份，也可两份一起交；一次补交后按合并结果重算**所有**圈的来源判定并记录快照，不止本次新增的行。
- 新增行追加；与已登记内容完全一致的行忽略并计入“重复一致”。
- 改写已登记的上游关系、同一文件内同一事件给出两个关系、同一圈同一来源给出两个不同事件、或合并后事件链成环 → **整次拒收**，SQLite 事务回滚，原有证据与各圈判定保持不变。
- 关联表引用了该批次中不存在的圈/来源读数 → 拒绝并说明具体圈与来源。

## 判定规则

- 计时是发车后累计毫秒数，首圈从 0 起算。
- 一个完整读数序列可行，当且仅当每圈 `c_i - c_{i-1} >= 最短可信圈时`（`c_0 = 0`）。
- 已核定的圈只能用核定读数；未核定的圈可在该圈全部来源读数中任选。
- 在所有完整可行序列上，求最快圈用时的最小值 `lower_ms` 和最大值 `upper_ms`。
- `upper_ms < 现有纪录` → **确定破纪录**；`lower_ms >= 现有纪录` → **确定未破纪录**（与纪录持平不算破）；否则 → **待核**。
- 无完整可行序列时不保存批次，并给出首个断裂圈的原因。

求解不穷举组合：

1. 前向可达性：逐圈按累计值排序后用二分 + 前缀计数，判断哪些读数能作为可行前缀的结尾。
2. 后向可达性：反向判断哪些读数能开始一个可行后缀。
3. 最快圈下界：取“位于至少一条完整可行路径上”的最小边权。若某条完整路径包含这条最轻边，则其最快圈恰为该边权。
4. 最快圈上界：对阈值 `T` 做二分，检查只允许 `c_i - c_{i-1} >= T` 的边时是否仍存在完整路径。谓词单调，复杂度约 `O(N·K·log K·log C)`，`K` 为每圈读数数，`C` 为时间范围，与组合数无关。

## 核定与并发

- 每圈可核定一条读数，也可取消核定。
- 提交时在一个 `BEGIN IMMEDIATE` 事务里读取数据库中的**其他圈最新核定状态**，把本圈替换为本次选择后重新求解。
- 采用按圈乐观并发控制：表单携带该圈当前的核定读数 ID。若同一圈已被另一位裁判抢先改定，返回 409 并保留原状；不同圈的并发核定则会依次生效（后提交者能看到先提交者的核定）。
- 若新核定导致没有完整可行序列，返回 409 并说明断裂位置，同样不修改任何状态。
- 只有重算可行时，才把新核定、版本号、结论、核定历史一并写入 SQLite；结论与核定在同一事务中提交。

## 数据表

- `sessions`：批次、最短可信圈时、现有纪录、当前版本。
- `laps` / `readings`：圈与各来源读数，`laps.pinned_reading_id` 记录核定。
- `conclusions`：每次重算的结论快照（版本号、上下限、状态）。
- `approvals`：每次核定操作的历史。
- `timing_events`：每个批次的事件登记（事件号、上游事件号或原始设备号，二者恰有其一）。
- `reading_links`：读数到事件的关联，每读数一条。
- `provenance_uploads`：每次补交的批次记录（类型、新增/重复行数）。
- `provenance_judgements`：每次补交后逐圈来源判定的快照。

## 已知限制

- CSV 只支持 UTF-8；暂不支持 XLSX 或多车手同场（每个批次一名车手）。
- 来源核查只按事件号/设备号做字符串比对，不校验时间戳是否物理一致；判定“同一台设备”不等于认定读数一定被误用，需裁判结合上游记录人工确认。
- 补交只允许追加；发现已登记关系写错时目前没有更正入口（需新建批次或由运维改库）。
- 未做登录/权限控制，网页应部署在可信网络或反向代理鉴权之后。
- SQLite 适合单场赛事的裁判组并发；极高并发场景需换 PostgreSQL。
